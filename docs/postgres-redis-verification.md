# PostgreSQL + Redis 验证报告

日期：2026-11-16。代码位于 `codex/postgres-redis` 工作分支，本报告记录本机执行结果，不代表生产 SLA 或真实模型质量。

## 执行环境

- Windows 11，Python 3.12.14。
- Docker 中的 PostgreSQL 16 / pgvector 与 Redis 7.4；PostgreSQL 与 Redis 均为真实服务。
- 两个独立 Python/FastAPI HTTP 进程，共享数据库和 Redis；每进程 PostgreSQL 连接上限 10，聊天总并发名额 16。
- 从原 SQLite 只读迁移到专用负载库：100 件商品、585 个 SKU、100 条描述、439 条 FAQ、453 条评价。原库保留。
- 真实模型、Embedding 和 Rerank 供应商没有参与负载测试；聊天使用 `DemoChatModel`，负载内容是“看看购物车”。语义召回、模型准确率、幻觉率不在本报告计算范围。

## 自动化测试

完整后端运行结果：**458 passed，7 skipped，5 warnings，17.43 秒**。跳过项属于原有条件测试；warning 为 FastAPI/AnyIO 弃用提示。

新增 20 项测试：18 项共享存储集成测试、2 项模型桥接回归测试。共享测试使用真实 SQL、向量距离算子和 Redis，覆盖：

- 同一个 SKU 满足预算上下限；品牌排除；商品变化后旧向量失效；子记录转移后两侧都失效。
- 两实例共享最近 10 条消息及工作记忆；删除 Redis 会话 key 后从检查点恢复。
- 同会话互斥、版本冲突、租约丢失、旧请求接管后的购物车与会话写入拒绝。
- 精确缓存键、并发回源合并、慢回源等待超时保护；Redis 不可连接时缓存回源、聊天协调拒绝执行。
- 多线程重复请求只加车一次；业务写入后抛错时事务全部回滚；相同请求 ID 不同参数拒绝执行。
- 并发偏好更新不丢失；图片向量与对比资料通过 PostgreSQL 访问并随商品变化失效。
- 只读 SQLite 迁移与非空目标库拒绝覆盖。
- 两个真实 HTTP 进程交替聊天、SSE、跨进程重试回放、购物车幂等和 CORS。
- 流尚未开始时关闭迭代器的资源释放；实际 HTTP 收到首个 session 帧后断开，3 秒内会话锁释放；明确未执行业务的错误允许复用请求 ID 重试。
- 24 次并发模型调用复用同一个事件循环；同步流关闭后取消异步生产者。

最后补充的 HTTP 断开与安全重试断言单独重跑：**1 passed，17 deselected，3.21 秒**。Compose 配置语法校验和 `git diff --check` 通过。独立代码审查发现的重要问题已修复并复核；可选容器 API 镜像没有重新构建，实际 HTTP 验证使用本机 Python 进程。

## 最终持续负载

闭环并发 8，每种负载目标持续 30 秒，两个 API 进程交替接收请求。每种负载先预热两个实例。P50/P95/P99 包含客户端观测的完整 HTTP 耗时。

| 负载 | 请求数 | 实际耗时 | 成功 / 错误 | 吞吐 | P50 | P95 | P99 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 商品详情查询 | 21,370 | 30.010 秒 | 21,370 / 0 | 712.10 req/s | 10.96 ms | 13.62 ms | 16.38 ms |
| 离线模型聊天，查看购物车 | 8,486 | 30.018 秒 | 8,486 / 0 | 282.69 req/s | 27.83 ms | 32.43 ms | 37.88 ms |

总计 **29,856 次 HTTP 请求，观测到 0 次错误**。[原始最终结果](benchmarks/postgres-redis-final-2026-11-16.json) 包含时间、配置和状态码计数。最后的统计代码将状态计数从重复扫描改为 Counter，避免负载结束后花费额外时间汇总，不改变样本或指标定义。

这里只能说明这两个本地工作负载在该时长内通过。短时间零错误不能证明长期零故障；单机 100 商品目录的吞吐不能外推到大目录、真实模型、多租户或百万并发。

## 失败记录与修复证据

首轮固定数量负载 1,000 次商品请求和 200 次离线聊天全部成功，见 [短批次结果](benchmarks/postgres-redis-2026-11-16.json)。随后持续负载暴露了短测试遗漏的问题：

1. [初始持续测试](benchmarks/postgres-redis-soak-2026-11-16.json)：商品请求全部成功；聊天 7,396 次中有 8 次传输超时，实际退出耗时延长到 57.742 秒。
2. [诊断复现](benchmarks/postgres-redis-chat-diagnostic-2026-11-16.json)：出现 ReadTimeout、ReadError、ConnectError。线程栈显示 Windows 在每次 `asyncio.run()` 创建事件循环时卡在 `socket._fallback_socketpair()`；24 次模型调用建立了 24 个循环，流关闭也没有取消生产者。
3. 修复为进程内共享模型事件循环、有限等待、有界流队列和生产者取消。新增的两个回归用例从失败变为通过。[桥接修复后结果](benchmarks/postgres-redis-after-2026-11-16.json) 无传输错误。
4. 继续补上数据库 fencing 和断连资源管理后，重新运行得到上面的最终结果。原始失败数据保留，不用成功测试替换失败记录。

## 尚未证明的能力

- 真实模型的准确率、幻觉率、向量召回率和供应商限流下的性能；新向量索引采用商品级证据，应另建标注集评测。
- 百万总请求、百万日活、百万并发是不同目标，本轮均未宣称达标。
- 长时间 soak、大规模商品、故障切换、主从复制、备份恢复、真实网络分区和跨机部署。
- 购物车仍使用演示用户；未新增认证与用户隔离。聊天在副作用结果未知时保留 pending，仍需要持久工作流或人工核对流程。
- PostgreSQL 检查点、fencing 行和请求账本尚未自动清理；应按审计及重试窗口制定保留和归档策略，不能随意删除不确定的 pending 记录。
